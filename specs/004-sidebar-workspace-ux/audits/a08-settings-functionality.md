## Findings

All five findings are **proposed, not implemented**. No implementation task is accepted by this audit.

### SET-001 (Medium): pending approval still presents Cancel as if it can cancel

- Category: interaction and asynchronous logic. `WorkspacePanel.tsx:28,84` has no pending state; Approve folder, Cancel and Escape remain active after submission.
- Trigger: approve the second exact folder with the IPC write held, click Cancel, then release the write. The dialog closes, but main saves the approval and it survives restart (S06/S07). This is a misleading cancellation affordance, not a main authority bypass: the owner did initially approve.
- Proposed improvement: single-flight Approving state; disable repeated submission and cancellation/Escape once the durable operation begins; retain exact folder identity until result. Rejected approval should keep a clear, fresh-choice recovery path. Cancellation before submission remains immediate and writes nothing.
- FR-009/011/013/018; US2/US5/US7. Verify delayed success, rejection, duplicate activation, Escape and exact saved identity. Shared modal semantics also need checking for recon busy cancellation, but that case is source-only here.
- Disposition: proposed 2026-09-05. Recommended first bounded slice.

### SET-002 (Medium): failed roster read is displayed as an empty roster without retry

- Category: interaction/logic. `WorkspaceRoster.tsx:216-233,304` uses null both before loading and after failure. S10 displays No roster yet despite main retaining a completed run and proposals, alongside an error and Run recon. There is no retry/refresh button.
- Proposed improvement: distinguish loading, loaded-empty, loaded-run and failed states. Add Retry for the exact workspace, retain truthful last-known status, and prevent new-run guidance from masquerading as read recovery. Handle poll rejection and exhausted collection reads explicitly.
- FR-007/011/018; US2/US6/US7. Verify initial failure/retry, slow collection, stale response, and exact existing run preservation. Five-read exhaustion/unhandled rejection risks are source-only, not reproduced incidents.
- Disposition: proposed 2026-09-05; renderer loading/recovery slice.

### SET-003 (Medium): provider prerequisites have no in-page recheck

- Category: interaction/logic. Readiness is loaded in Store startup and updated through events; ProviderReadiness provides no Check again action. Returning to Settings does not request fresh evidence.
- S13 injects an old missing-provider response while the main fixture is ready. One startup read remains the total after section return; no refresh control exists. Explicit main recheck restores Available. This is controlled stale-cache evidence, not proof of a particular real installation failure.
- Proposed improvement: explicit Check again with pending/error/last-checked feedback and provider-scoped results. Preserve selected workspace; never install, authenticate or launch automatically. Rename the Agents heading to Provider readiness to distinguish it from the Agents destination.
- FR-009/010/011/018; US5/US6/US7. Validate one provider failing independently, stale response rejection and launch eligibility after fresh evidence.
- Disposition: proposed 2026-09-05.

### SET-004 (Medium): Settings still overflows at 960px and 200% text

- Category: visual/interaction. S03 measures guided-setup client width 657 versus scroll width 698; setup cards extend to x985.84 beyond the 960px viewport. The inspected narrow capture clips explanatory text and requires horizontal scrolling despite the corrected sidebar.
- Source: `styles/guided-setup.css` grid tracks and min-content sizing; this is inner Settings layout, not evidence that ATT-003 regressed.
- Proposed improvement: shrinkable outer/child tracks, wrapped paths and facts, stacked evidence/action layouts. Keep full exact folder identity available. Verify normal/medium/narrow widths with 100%/200% text and disclosure dialogs.
- FR-009/012; US5/US6. Shared A09 and AGT-003 reconciliation concern; only Settings sample reproduced here.
- Disposition: proposed 2026-09-05.

### SET-005 (Medium): unaccepted recon proposals disappear on restart without lifetime guidance

- Category: lifecycle/interaction. Main recon runs are in a Map and getRun returns null after restart. S09/S11 show completed proposals before restart, then No roster yet afterward while the stopped session and imported profile persist.
- Proposed improvement: explicitly disclose temporary unaccepted proposals and their restart lifetime, with a deliberate review/export path. If durable resume is desired, route persistence/revalidation design to the recon capability; do not silently treat a copy fix as durable recovery. No automatic rerun or import.
- FR-007/009/013/018; US3/US5/US7. Verify preserved accepted profile, honest empty/expired state and no provider relaunch. Persistent proposal recovery requires separate design acceptance.
- Disposition: proposed 2026-09-05; presentation clarification is bounded, persistence is a capability referral.

## Proposed interaction design

Keep Settings' three groups: Workspace access, Provider readiness, Application health. Folder approval has choosing, reviewing, approving and result states, with exact identity visible throughout. Cancellation ends review before submission; an in-flight durable write is clearly pending until completion. Workspace revocation retains main-owned active-session protection.

Give each roster an explicit loading/error/empty/run state, a Retry action for failed reads, exact run/session navigation for owner stop, and clear temporary-proposal lifetime. Reviewing one proposal remains separate from accepting one profile. Check again refreshes readiness only. Launch/recon confirmation continues to disclose actual execution limits and never claims filesystem confinement.

Retain existing guarded Missions return. A dedicated return-to-origin convenience can be reconciled in A09 after remaining composer excursions are verified. First recommendation is SET-001, followed by SET-002, SET-003 and SET-004; decide the bounded SET-005 lifetime wording versus durable capability separately.

## Section acceptance summary

- Visual/interaction: observed failures in pending approval, error/empty messaging, recheck discoverability and reflow. Two captures inspected.
- Logic: main folder identity, duplicate handling and live revocation policy pass sampled runtime/contract checks. Renderer async state and recon lifetime need improvements. See source-only caveats above.
- Functionality: normal approval/revocation, local fixture launch/recon, owner stop, reviewed import and accepted-profile persistence verified with independent reads. Pending approval cancellation and recon restart limitations reproduced.
- Remaining gaps: actual external provider install/auth/version transitions; Windows folder identity UI variants (native integration covered separately); full storage degradation/repair UI; initial startup appInfo/readiness failure; stale proposal/provider replacement races; collection failure/exhaustion; full keyboard/screen-reader/large-inventory/reflow matrix; edited composer prerequisite excursion. These are pending, not passed.
- A08 now has a source/observed audit with explicit gaps. A09 cross-section reconciliation and earlier section gaps remain open. Audit completion is distinct from product acceptance.
